## Общие правила

- Профиль выбирается по назначению кода, а не только по языку или расширению
  файла. Переиспользуемый драйвер относится к профилю библиотек, а связывающий
  его с конкретной платой код — к профилю прикладной прошивки.
- Следуйте стилю существующего модуля, если он не противоречит этому документу
  или явно зафиксированным локальным правилам репозитория.
- Имена должны описывать назначение сущности; избегайте необъяснимых сокращений.
- Комментарии объясняют причину, ограничение, контракт или особенность
  аппаратуры, а не повторяют очевидный код. Язык комментариев задаётся каждым
  профилем отдельно.
- Проектные текстовые файлы хранятся в UTF-8 без BOM. При изменении файла
  сохраняйте принятый в нём тип окончания строк.
- Не изменяйте вендорный или сгенерированный код без отдельной необходимости.
  Его стиль не является безусловным образцом для нового кода.
- Используйте форматтеры и статические анализаторы, закреплённые в репозитории.
- Новый слой, namespace, механизм диспетчеризации, владения ресурсом или
  межмодульный контракт предварительно обсуждается с командой.

### Отступы и настройка редактора

- Для одного уровня отступа используется один настоящий символ TAB, а не
  последовательность пробелов.
- Визуальная ширина TAB — четыре пробела. TAB нельзя автоматически заменять
  пробелами при вводе или сохранении файла.
- Не смешивайте TAB и пробелы в начале строк одного блока. Пробелы допустимы
  после структурного отступа только для локального табличного выравнивания.
- Автоматическое определение отступов редактором отключается, чтобы настройки
  случайного открытого файла не меняли стиль проекта.
- Для VS Code закрепите эквивалентные настройки в конфигурации репозитория:

```json
{
    "editor.detectIndentation": false,
    "editor.insertSpaces": false,
    "editor.tabSize": 4
}
```

### Референсный код

Практическим референсом оформления embedded-кода служит каталог
[Embedded репозитория Telega](https://github.com/r3m4k/Telega/tree/master/Embedded).
Он используется как пример структуры файлов, секционных комментариев и
группировки кода. При расхождении референсного кода с настоящим документом
приоритет имеют правила настоящего документа.

## Профиль библиотек для микроконтроллеров

### Область применения

Профиль применяется к переиспользуемым C-библиотекам и драйверам
микроконтроллеров, оформленным парой `.h` / `.c`. Заголовочный файл описывает
публичный контракт, исходный файл содержит реализацию и приватные сущности.

Комментарии и Doxygen-документация в C/C++ пишутся на английском языке. Это
правило действует и для внутренних комментариев, и для описаний публичного API.

### Директории и размещение файлов

Рекомендуемая структура самостоятельной библиотеки:

```text
library_name/
├── include/
│   └── library_name/
│       ├── module_name.h
│       └── another_module.h
├── src/
│   └── library_name/
│       ├── module_name.c
│       └── another_module.c
└── tests/
```

- Публичные `.h` сохраняются только в `include/<library_name>/`. Пользователь
  подключает их как `#include "module_name.h"`.
- В build system каталог `include/<library_name>/` добавляется в include search
  path компилятора или препроцессора (`-I`, `target_include_directories` и
  эквивалентные настройки).
- Короткое имя заголовка требует уникальных имён среди одновременно
  подключённых библиотек. При коллизии модуль переименовывается с уточняющим
  префиксом; зависимость от порядка include paths не допускается.
- Реализации `.c` сохраняются в `src/<library_name>/`.
- Приватный заголовок, необходимый нескольким исходным файлам библиотеки,
  сохраняется в `src/<library_name>/internal/` и не добавляется в публичный
  include path.
- Если библиотека состоит из одного небольшого модуля, подкаталог `internal/`
  не создаётся без необходимости.
- Имена директорий пишутся на английском в `lower_snake_case` и обозначают
  ответственность или предметную область: `communication`, `sensors`,
  `data_containers`. Не называйте каталоги по фамилии автора, этапу разработки
  или временной сортировке (`new`, `old`).
- Не создавайте размытые `common`, `misc`, `helpers` и `utils`, пока нельзя
  сформулировать единую ответственность их содержимого. Если каталог становится
  свалкой, разделите его по подсистемам.
- При большом числе модулей деревья `include/<library_name>/` и
  `src/<library_name>/` зеркально повторяют подсистемы, чтобы заголовок и
  реализация находились по одинаковому относительному пути.
- Один модуль обычно представлен одной парой `module_name.h` / `module_name.c`.
  Новый каталог создаётся для группы связанных модулей, а не для единственного
  файла без самостоятельной предметной области.
- Если подходящее имя или граница директории неочевидны, задайте вопрос тимлиду
  в общем командном чате. Такие вопросы не обсуждаются в личных сообщениях:
  решение должно быть видно всей команде.

Публичные имена имеют префикс модуля:

- файл: `module_name.h`, `module_name.c`;
- функция: `MODULE_ActionObject()`;
- тип: `MODULE_NameTypeDef`;
- значение перечисления или публичная константа: `MODULE_Name_Value`;
- проверочный макрос: `IS_MODULE_NAME()`;
- приватная функция или переменная: `snake_case`.

Не копируйте зарезервированные идентификаторы SPL с двумя начальными
подчёркиваниями. Include guard вида `__MODULE_H` запрещён.

### Структура заголовочного файла

Секции `.h` располагаются в следующем порядке:

```c
/** ****************************************************************************
 * @file    module_name.h
 * @brief   Short purpose of the module
 * @author  Author name
 * @date    Month Year
 *
 * @details Supported peripherals, constraints, and usage requirements.
 **************************************************************************** */

/* Define to prevent recursive inclusion -------------------------------------*/
#ifndef MODULE_NAME_H
#define MODULE_NAME_H

#ifdef __cplusplus
extern "C" {
#endif

/* Includes ------------------------------------------------------------------*/

/* Exported types ------------------------------------------------------------*/

/* Exported constants --------------------------------------------------------*/

/* Exported macro ------------------------------------------------------------*/

/* Exported functions --------------------------------------------------------*/

#ifdef __cplusplus
}
#endif

#endif /* MODULE_NAME_H */
```

- Include guard строится из полного имени файла в `UPPER_SNAKE_CASE`.
- `extern "C"` обязателен, если C-библиотека может подключаться из C++.
- Заголовок подключает только зависимости, необходимые его публичным
  объявлениям. Зависимости реализации подключаются в `.c`.
- В `Exported types` размещаются перечисления, структуры и callback-типы.
- В `Exported constants` размещаются группы констант и проверочные макросы.
- В `Exported macro` остаются только макросы публичного API. Не используйте
  макрос вместо функции без причины, связанной с компиляцией или аппаратурой.
- В `Exported functions` объявления группируются по назначению: сброс и
  инициализация, конфигурация, чтение и запись, прерывания, получение состояния.
- Стандартные секции сохраняются даже временно пустыми: единый каркас упрощает
  навигацию между драйверами.

Если документация собирается в общие группы Doxygen, библиотека и драйвер
оформляются через `@addtogroup` / `@defgroup`, а содержимое ограничивается
`@{` и `@}`. Не создавайте группу ради одного очевидного объявления.

### Структура исходного файла

Секции `.c` располагаются в следующем порядке:

```c
/** ****************************************************************************
 * @file    module_name.c
 * @brief   Module implementation
 * @author  Author name
 * @date    Month Year
 *
 * @details Implementation details and the required driver usage sequence.
 **************************************************************************** */

/* Includes ------------------------------------------------------------------*/
#include "module_name.h"

/* Private typedef -----------------------------------------------------------*/

/* Private define ------------------------------------------------------------*/

/* Private macro -------------------------------------------------------------*/

/* Private variables ---------------------------------------------------------*/

/* Private function prototypes -----------------------------------------------*/

/* Private functions ---------------------------------------------------------*/
```

- Собственный заголовок подключается первым, затем платформенные зависимости.
- Непубличные сущности остаются в `.c`. Приватные функции и переменные имеют
  внутреннее связывание через `static`.
- Приватные типы, константы, макросы, переменные и прототипы не смешиваются.
- Публичные функции реализуются в том же порядке и в тех же смысловых группах,
  в которых объявлены в `.h`.
- Внутри группы функции идут от общей настройки к частным операциям.

### Типы и структуры

- Для взаимоисключающих именованных состояний используется `typedef enum`, а
  не набор несвязанных числовых `#define`.
- Значения перечисления получают префикс модуля. Знаки `=` разрешается
  выравнивать внутри компактного однородного блока.
- Конфигурационная структура объединяет параметры одной операции и оканчивается
  суффиксом `TypeDef`.
- Перед публичной структурой или перечислением размещается Doxygen-блок с
  `@brief`. Поля документируются справа через `/*!< ... */`.
- Для поля описывается назначение, диапазон, единица измерения или ссылка
  `@ref` на набор значений, а не повторяется его тип.

```c
/**
 * @brief UART initialization parameters.
 */
typedef struct
{
	uint32_t UART_BaudRate;  /*!< Baud rate in bits per second. */
	uint32_t UART_Mode;      /*!< Mode from @ref UART_Mode_Values. */
	uint32_t UART_Parity;    /*!< Parity from @ref UART_Parity_Values. */
} UART_InitTypeDef;
```

### Константы и макросы

- Связанные публичные константы объединяются в смысловые Doxygen-группы.
- Имя, значение и правый комментарий выравниваются внутри одной компактной
  таблицы. Независимые группы не связываются общим выравниванием.
- Для регистровых масок явно фиксируется целевой тип. Целочисленные литералы
  получают подходящий суффикс (`U`, `UL`) или необходимое API приведение.
- Аргументы функционального макроса и результирующее выражение заключаются в
  скобки.
- Многострочный макрос продолжается через `\`; следующие строки
  выравниваются по началу логического выражения.
- Проверочный макрос размещается сразу после проверяемого типа или набора.

```c
#define UART_MODE_RX       ((uint32_t)0x00000001U)  /*!< Receive enabled. */
#define UART_MODE_TX       ((uint32_t)0x00000002U)  /*!< Transmit enabled. */
#define UART_MODE_RX_TX    ((uint32_t)0x00000003U)  /*!< Receive and transmit enabled. */

#define IS_UART_MODE(MODE) (((MODE) == UART_MODE_RX)    || \
                            ((MODE) == UART_MODE_TX)    || \
                            ((MODE) == UART_MODE_RX_TX))
```

### Функции и Doxygen

В качестве введения в синтаксис, команды и группировку см. статью [«Документируем код эффективно при помощи Doxygen»](https://habr.com/ru/articles/252101).

- Публичная функция выполняет одну операцию и начинается с префикса модуля.
- Парные операции называются симметрично: `Enable` / `Disable`,
  `Set` / `Reset`, `Read` / `Write`, `Start` / `Stop`.
- Сброс, заполнение структуры значениями по умолчанию и применение
  конфигурации образуют отдельную группу.
- Входные параметры проверяются в начале функции. Для SPL-совместимого слоя
  допускаются проверочные макросы и `assert_param()`.
- Публичный контракт документируется перед объявлением в `.h`. В `.c` он
  не дублируется; там объясняются только алгоритм и аппаратные ограничения.

```c
/**
 * @brief      Configures the selected DMA channel.
 * @param[in]  channel  DMA channel from @ref DMA_Channel_Values.
 * @param[in]  config   Pointer to an initialized configuration structure.
 * @return     Configuration status.
 * @retval     MODULE_STATUS_OK     Configuration completed successfully.
 * @retval     MODULE_STATUS_ERROR  Parameters or state are invalid.
 * @note       Call this function only while the channel is disabled.
 */
MODULE_StatusTypeDef MODULE_Init(
	MODULE_ChannelTypeDef channel,
	const MODULE_InitTypeDef *config
);
```

- `@brief` обязателен для каждой публичной сущности.
- Текст Doxygen-комментариев пишется на английском; имена тегов остаются в
  стандартной форме Doxygen.
- `@param[in]`, `@param[out]`, `@param[in,out]` задают направление данных.
- `@return` описывает смысл результата, `@retval` — именованные значения.
- `@note`, `@warning`, `@pre`, `@details` добавляются только при наличии
  соответствующего контракта.
- Не пишите `@param None`, `@return None` или `@retval None` для `void`.
- Теги и начало описаний выравниваются внутри блока; перенос начинается под
  текстом первой строки.

### Форматирование и выравнивание

- Каждый уровень отступа оформляется одним TAB по общим правилам документа.
- Открывающая скобка функции, `if`, `else`, `for`, `while`, `switch`
  располагается на новой строке.
- После управляющего слова ставится пробел: `if (condition)`.
- Указатель записывается у имени переменной: `uint8_t *buffer`.
- Однотипные объявления, поля, `#define` и правые комментарии выравниваются
  только внутри короткого смыслового блока.
- Продолжение выражения выравнивается по открывающей скобке или первому
  операнду; в пределах блока используется один способ.
- Пустая строка разделяет проверки, подготовку данных, работу с регистрами и
  формирование результата.

## Профиль прикладного кода прошивки

### Область применения

Профиль применяется к C/C++-коду конкретного устройства: `main`, конфигурации
платы, связыванию драйверов, обработчикам прерываний, протоколам устройства,
датчикам, фильтрам и стадиям работы программы.

Комментарии и Doxygen-документация в пользовательском C/C++ пишутся на
английском языке независимо от языка интерфейса программы.

### Директории и размещение файлов

Для прошивки, созданной вокруг CubeMX или сходного каркаса, используется
структура `inc` / `src`:

```text
firmware/
├── inc/
│   ├── app/
│   ├── communication/
│   ├── sensors/
│   └── main.h
└── src/
    ├── app/
    ├── communication/
    ├── sensors/
    └── main.cpp
```

- Пользовательские `.h` и `.hpp` сохраняются в `inc/`, реализации `.c` и
  `.cpp` — в `src/`.
- `main.h` находится в `inc/`, `main.c` или `main.cpp` — в `src/`.
- Приватный заголовок, используемый только реализацией одной подсистемы,
  сохраняется рядом с ней в `src/<subsystem>/internal/`. Он не добавляется в
  общий include path.
- Деревья `inc/` и `src/` зеркально повторяют подсистемы. Например,
  `inc/communication/packet.hpp` соответствует
  `src/communication/packet.cpp`.
- Директории называются на английском в `lower_snake_case` и отражают
  ответственность: `communication`, `sensors`, `filters`, `data_containers`,
  `platform`, `app`.
- Не разделяйте дерево только по языкам на каталоги `c` и `cpp`: сначала важна
  подсистема, а язык виден из расширения. Отдельный языковой каталог оправдан,
  только если он представляет самостоятельную библиотеку или ABI-границу.
- Код конкретной платы остаётся в `platform` или каталоге платы. Повторно
  используемый драйвер без зависимости от приложения должен быть вынесен в
  библиотеку и оформлен по библиотечному профилю.
- Не используйте временные и размытые имена вроде `aaa_project_files`, `new`,
  `old`, `misc`. Каталог создаётся, когда для группы файлов можно назвать одну
  ответственность.
- Если подходящее имя или граница директории неочевидны, задайте вопрос тимлиду
  в общем командном чате. Не переносите обсуждение в личные сообщения, чтобы
  решение и его причины оставались доступными всей команде.

Если генератор проекта требует `Core/Inc` и `Core/Src`, сохраняйте его структуру:
не создавайте параллельные `inc` / `src`. Логические подкаталоги и остальные
правила остаются теми же.

### Порядок кода в `main.c` и `main.cpp`

На основе устойчивой структуры прикладного `main.cpp` используется следующий
порядок:

1. Подключения стандартных, платформенных и проектных заголовков.
2. Константы времени компиляции и макросы файла.
3. Локальные типы и объявления функций.
4. Обязательное платформенное состояние и объекты приложения, сгруппированные
   по подсистемам: связь, таймеры, датчики, фильтры, пакеты, команды, стадии.
5. `main()` с кратко отделёнными этапами запуска и основным циклом.
6. Функции инициализации оборудования.
7. Обработчики прерываний и callback-функции.
8. Обработчики стадий программы и команд.
9. Формирование предопределённых сообщений.
10. Системные hooks и функции совместимости с вендорным кодом.

Необходимое сгенерированное или вендорное состояние отделяется секцией с
пометкой `DO NOT MODIFY` и не смешивается с пользовательскими объектами.

### Группировка кода

Стандартные секции оформляются в стиле CubeMX:

```cpp
/* Includes ------------------------------------------------------------------*/
/* Defines -------------------------------------------------------------------*/
/* Global variables ----------------------------------------------------------*/
```

Большой самостоятельный блок получает именованный разделитель:

```cpp
/* ****************************************************************************
 * Sensors, filters, and data packages
 **************************************************************************** */
```

Семейство связанных функций получает трёхстрочный разделитель:

```cpp
// -----------------------------------------------------------------------------
// Program stage handlers
// -----------------------------------------------------------------------------
```

- Разделитель применяется к группе сущностей с общей задачей, а не к каждой
  отдельной сущности.
- Не оставляйте длинный разделитель без названия: читатель должен понимать
  назначение следующего блока без просмотра его содержимого.
- Глобальные объекты группируются по назначению: связь, таймеры, датчики,
  фильтры, данные, команды, стадии программы.
- Внутри `main()` короткий комментарий обозначает этап: аппаратная
  инициализация, запуск сервисов, начальное состояние, основной цикл.
- Многострочный предупреждающий блок применяется только для ограничения,
  влияющего на корректность или время выполнения, и начинается с `WARNING:`.
- Закомментированный код не хранится как вариант конфигурации. Используйте
  систему сборки, конфигурационный макрос или историю версий.

### Пользовательский код на C

#### Структура и именование

- Публичный `.h` содержит Doxygen-заголовок файла, include guard, подключения,
  константы, типы, объявления `extern` и прототипы функций именно в таком
  порядке.
- `.c` подключает собственный заголовок первым, затем зависимости реализации;
  после них идут приватные типы, константы, состояние, прототипы и функции.
- Файлы, функции и переменные именуются в `snake_case`; типы — в
  `snake_case_t`; макросы и значения перечислений — в `UPPER_SNAKE_CASE`.
- Публичная функция получает префикс подсистемы: `sensor_init()`,
  `sensor_read_data()`. Приватная функция объявляется `static`.
- Для функции без параметров в прототипе явно пишется `(void)`.
- Глобальные изменяемые переменные не помещаются в заголовок без необходимости.
  Если внешний доступ является частью контракта, используется `extern`, а
  определение остаётся в одном `.c`.

#### Doxygen и форматирование

- Публичные типы, поля структур и функции документируются на английском по
  правилам раздела «Функции и Doxygen» библиотечного профиля.
- Каждый уровень отступа оформляется одним TAB по общим правилам документа.
- Открывающая скобка функции и управляющей конструкции размещается на новой
  строке.
- Указатель записывается у имени: `const uint8_t *buffer`.
- Сложное условие переносится по одному логическому члену на строку; оператор
  остаётся в начале продолжения либо в конце предыдущей строки единообразно во
  всём файле.
- Объявляйте переменную максимально близко к месту первого использования и
  инициализируйте при объявлении.
- Не смешивайте объявления и выполняемый код в одной строке; тело `if`, `for`
  или `while` всегда заключается в фигурные скобки.

Пример форматирования C-кода:

```c
/**
 * @brief   Processes sensor samples and updates the current average.
 * @param   context       Sensor processing context.
 * @param   samples       Input samples.
 * @param   sample_count  Number of input samples.
 * @return  Processing status.
 */
sensor_status_t sensor_process(sensor_context_t *context,
							   const uint16_t *samples,
							   size_t sample_count){
	if ((context == NULL)
		|| (samples == NULL)
		|| (sample_count == 0U))
	{
		return SENSOR_STATUS_INVALID_ARGUMENT;
	}

	uint32_t sample_sum = 0U;

	for (size_t index = 0U; index < sample_count; ++index){
		sample_sum += samples[index];
	}

	context->average = sample_sum / sample_count;
	return SENSOR_STATUS_OK;
}
```

### Пользовательский код на C++

#### Структура файлов C++

Публичный `.hpp` начинается с Doxygen-заголовка, затем следуют include guard и
секции верхнего уровня:

```cpp
/** ****************************************************************************
 * @file    Example.hpp
 * @brief   Short purpose of the file
 * @author  Author name
 * @date    Month Year
 *
 * @details Responsibilities, constraints, and exported types.
 **************************************************************************** */

/* Define to prevent recursive inclusion -------------------------------------*/
#ifndef EXAMPLE_HPP
#define EXAMPLE_HPP

/* Includes ------------------------------------------------------------------*/

/* Defines -------------------------------------------------------------------*/

/* Usings --------------------------------------------------------------------*/

/* Global variables ----------------------------------------------------------*/

#endif /* EXAMPLE_HPP */
```

- Guard строится из полного имени файла без начальных подчёркиваний.
- Подключения делятся пустыми строками на стандартные, платформенные и
  проектные.
- Каждый `.hpp` самостоятельно подключает всё необходимое публичному API.
- Пустые `Defines`, `Usings`, `Global variables` разрешается не добавлять.
- Определения глобальных объектов не помещаются в заголовок. Допустимы
  `inline constexpr`, шаблоны и необходимые объявления `extern`.
- Нешаблонный класс разделяется на `.hpp` и `.cpp`. Header-only сохраняется для
  шаблонов и модулей, где этот подход уже принят.
- Внутри класса объявления группируются по доступу и назначению. Не переключайте
  `public`, `protected`, `private` без необходимости.
- Закрывающая скобка namespace получает комментарий:
  `} // namespace decoder`.

#### Именование

- Классы, структуры, перечисления и типовые параметры шаблона — `PascalCase`.
- Функции, методы, переменные и нетиповые параметры шаблона — `snake_case`.
- Константы времени компиляции и макросы — `UPPER_SNAKE_CASE`.
- Обработчик получает суффикс `_handler`, callback-тип — `_handler_t` или
  осмысленный псевдоним в `PascalCase`.
- Новый код не продолжает смешение `Init()` / `init()` и `ReadData()` /
  `read_data()`, встречающееся в старом коде: используется `snake_case`.
  Имена внешнего API не переименовываются.
- Используйте существующий подходящий namespace. Новый namespace обсуждается с
  командой.

#### Классы, шаблоны и перечисления

- Публичный API класса минимален; детали реализации остаются `private` или
  `protected`.
- Не создавайте набор тривиальных getter/setter для каждого поля. Класс должен
  предоставлять операции предметной области и сохранять свои инварианты. Для
  простого пассивного набора данных используйте структуру с публичными полями;
  getter добавляйте для действительно закрытого состояния, setter — когда при
  изменении выполняется проверка или поддерживается инвариант.
- Если объект невозможно корректно создать без обязательных параметров,
  конструктор без параметров явно удаляется: `Device() = delete;`.
- Аналогично удаляйте копирование или перемещение, если владение аппаратным
  ресурсом не допускает такую операцию. `= default` используется только для
  семантически корректной операции.
- Для шаблонного параметра, от которого требуется конкретный интерфейс или
  набор операций, обязателен concept. Используйте стандартный concept, если он
  подходит; иначе определите узкий именованный concept предметной области.
- `static_assert` применяется для ограничений значений и размеров, которые
  concept выразить не может. `if constexpr` используется для выбора реализации
  на этапе компиляции.
- Типовые параметры называются по роли: `ValueType`, `Derived`, `Pin`;
  нетиповые описывают значение: `buffer_size`, `irq_number`.
- Используйте `enum class`, если не требуется совместимость с C или неявное
  преобразование к целому.
- Значения перечисления документируются через `///<`, если имя не раскрывает
  аппаратный или протокольный смысл.
- Для типизированных констант предпочитайте `constexpr`; макросы оставляйте
  для условной компиляции, вендорных API и препроцессора.
- Запрещённые операции объявляются через `= delete`, стандартные реализации —
  через `= default`.

#### Doxygen-комментарии

- Каждый публичный `.hpp`, класс и публичный метод документируется на английском
  языке.
- В заголовке файла обязательны `@file`, `@brief`; `@details`, `@date`,
  `@author` добавляются по шаблону репозитория.
- Для класса используются `@brief`, `@details`, `@tparam`, при
  необходимости — `@warning`, `@note`, `@pre` и пример.
- Для функции используются `@brief`, `@param`, `@return`; контекст вызова
  и побочные эффекты фиксируются через `@note` или `@warning`.
- Короткие поля и значения перечисления документируются через `///<`.
- Для ISR обязательно указываются контекст вызова, допустимость блокировок и
  способ передачи работы в основной цикл.
- Doxygen описывает контракт; внутренние комментарии — стадии алгоритма,
  работу с регистрами и причины синхронизации.

```cpp
/**
 * @brief   Passes one byte to the decoder state machine.
 * @param   byte  Next byte from the input stream.
 * @details This method is called from the USART ISR and never blocks.
 */
void process_byte(uint8_t byte);
```

#### Форматирование и выравнивание

- Каждый уровень отступа оформляется одним TAB по общим правилам документа.
- Открывающая скобка класса, namespace, функции и управляющей конструкции
  остаётся в строке объявления: `if (ready) {`.
- После `if`, `for`, `while`, `switch` ставится пробел.
- Указатель и ссылка записываются у типа: `const Message* message`,
  `const Config& config`.
- Длинные списки параметров шаблона, базовых классов, аргументов функции или
  вызова переносятся по одной сущности на строку.
- Инициализаторы конструктора при переносе размещаются по одному на строку.
- В коротком однородном блоке разрешается выравнивать инициализаторы и правые
  комментарии. Независимые объявления общим выравниванием не связываются.
- Между смысловыми стадиями функции оставляется пустая строка. Несколько
  действий не сжимаются в одну строку.
- В C++ используются именованные casts; C-style cast в новом коде запрещён.

Пример форматирования C++-кода:

```cpp
/**
 * @brief   Reads and scales one sensor value.
 * @param   request   Read parameters.
 * @param   response  Destination for the processed value.
 * @return  `true` when the value has been processed successfully.
 */
bool SensorController::process(
	const ReadRequest& request,
	ReadResponse* response) {
	
	if (response == nullptr) {
		return false;
	}

	const auto raw_value = peripheral_.read(request.channel);
	const auto scaled_value = static_cast<float>(raw_value)
		* request.scale;

	response->value = filter_.apply(scaled_value);
	response->valid = true;

	return true;
}
```

### Ограничения embedded-кода

#### Детерминированность и память

- Время выполнения операции должно иметь понятную верхнюю границу. Ожидание
  периферии ограничивается таймаутом; бесконечный busy-wait допустим только в
  явно документированном аварийном состоянии.
- Динамическая аллокация в ISR и горячих путях запрещена. В остальном коде она
  допускается только после оценки фрагментации, времени выполнения и поведения
  при нехватке памяти; после завершения инициализации предпочтительна работа без
  heap.
- Для очередей, пулов и буферов с известной ёмкостью используются статические
  контейнеры. Переполнение имеет явное и проверяемое поведение.
- Большие локальные массивы не размещаются на стеке. Для каждой задачи RTOS
  оценивается максимальное потребление стека и оставляется измеренный запас.
- Рекурсия, массивы переменной длины и алгоритмы без ограниченной глубины в
  прошивке не используются без отдельного обоснования.
- Владение ресурсом всегда однозначно. В C++ используется RAII без зависимости
  от исключений; владеющий raw pointer не применяется.

#### Типы и работа с данными

- Для регистров, протоколов и сериализованных данных используются типы точной
  ширины из `<stdint.h>` / `<cstdint>`.
- Знаковость, переполнение, сужающие преобразования и арифметика разных типов
  проверяются явно. Не полагайтесь на неявное преобразование отрицательного
  значения в беззнаковое.
- Порядок байтов, размер поля и выравнивание протокола задаются явно. Не
  сериализуйте структуру через копирование её памяти, если layout и padding не
  закреплены протоколом и статическими проверками.
- Константные таблицы и неизменяемые конфигурации объявляются `const` /
  `constexpr`, чтобы компилятор мог разместить их во flash.
- Каждая переменная и структура инициализируется до первого чтения. Значение
  после сброса периферии не считается известным без подтверждения документацией.

#### Прерывания и конкурентный доступ

- ISR выполняет минимум работы: считывает или фиксирует данные, очищает
  аппаратный флаг и передаёт дальнейшую обработку в основной контекст.
- Блокирующие операции, логирование, выделение памяти и длительные вычисления в
  ISR запрещены.
- Разделяемые с ISR данные имеют явно описанную модель синхронизации. `volatile`
  заставляет выполнить доступ к объекту, но не обеспечивает атомарность, порядок
  памяти или взаимное исключение.
- Для взаимодействия контекстов используются атомики, короткие критические
  секции либо специализированная SPSC-очередь. Выбранный механизм должен
  соответствовать числу производителей и потребителей.
- При прямой работе с регистрами используются типы, квалификаторы, барьеры и
  intrinsic-функции, рекомендованные производителем ядра и микроконтроллера.
- Приоритеты прерываний выбираются с учётом максимальной длительности ISR и
  правил вызова API RTOS. Высокоприоритетный ISR не вызывает недопустимые для его
  приоритета функции ядра.

#### Полиморфизм и обработка ошибок

- Исключения C++ в embedded-коде полностью запрещены. Сборка должна отключать их,
  если toolchain предоставляет соответствующий флаг. Ошибки возвращаются через
  status enum, специальный result-тип или выходной параметр.
- `virtual` разрешён, когда динамический полиморфизм существенно упрощает
  интерфейс и его стоимость оправдана. Перед применением оцените размер vtable,
  дополнительный указатель в объекте, косвенный вызов и невозможность части
  оптимизаций.
- Полиморфный базовый класс имеет виртуальный деструктор, если объект может
  уничтожаться через указатель на базовый класс. Методы-наследники помечаются
  `override`, окончательные классы или методы — `final`.
- Не используйте `virtual` в ISR и критичных по времени циклах без измерения
  worst-case execution time. Не создавайте глубокую иерархию ради повторного
  использования кода; композиция обычно проще.
- RTTI по умолчанию отключён. Если нужны `dynamic_cast` или `typeid`, это
  отдельное архитектурное решение с оценкой стоимости.
- Если интерфейс и набор реализаций известны во время компиляции, предпочитайте
  concept, шаблон, CRTP или явную таблицу функций. Это рекомендация, а не запрет
  оправданного динамического полиморфизма.
- Любой status проверяется либо сознательно игнорируется с комментарием.
  Ошибка переводит устройство в определённое безопасное состояние.

## Профиль Python

### Структура модуля

Каждый непустой модуль начинается с docstring о его назначении. Объявление
кодировки UTF-8 в Python 3 не требуется; сохраняйте его только в файлах, где оно
уже является частью принятого шаблона.

Импорты делятся на три явные секции, даже если одна из них пуста:

```python
"""Краткое описание назначения модуля."""

# System imports
import asyncio
from pathlib import Path

# External imports
from pydantic import BaseModel

# User imports
from app_config.app_config import AppConfig

#############################################
```

- `System imports` — стандартная библиотека; `External imports` — сторонние
  пакеты; `User imports` — модули проекта.
- Внутри секции сначала идут `import`, затем `from ... import ...`; порядок
  поддерживается форматтером репозитория.
- Длинный `from ... import ...` оформляется в скобках, по одному имени на
  строку, с завершающей запятой.
- После импортов идут модульные константы, типы, исключения, публичные классы и
  функции, затем приватные вспомогательные функции.
- `__init__.py`, содержащий только реэкспорт API, может не иметь развёрнутого
  docstring.

### Группировка кода

В крупном модуле или классе используется трёхстрочный разделитель:

```python
# =============================================================
# =================== Обработчики сигналов ====================
# =============================================================
```

- Разделы создаются для публичного API, контекстного менеджера, обработчиков,
  абстрактных методов, фоновых задач и внутренней логики.
- Короткий класс или несколько близких функций разделителя не требуют.
- Между сущностями верхнего уровня оставляются две пустые строки, между методами
  класса — одна.
- Большой класс разбивается на небольшие методы по этапам работы.

### Именование и типизация

- Классы и исключения — `PascalCase`; функции, методы, параметры, переменные и
  модули — `snake_case`.
- Константы модуля — `UPPER_SNAKE_CASE`; приватные константы получают один
  начальный `_`, например `_RESPONSE_TIMEOUT_SECONDS`.
- Приватные методы и атрибуты получают один `_`. Двойное подчёркивание не
  используется без необходимости name mangling.
- Протоколы заканчиваются на `Protocol`, базовые исключения подсистемы — на
  `Error` или `Exception`.
- Исключение наследуется от наиболее точного встроенного или базового
  исключения подсистемы, а не от голого `Exception`.
- Все параметры, возвращаемые значения и атрибуты экземпляров имеют type hints.
- Для функции без результата явно указывается `-> None`.
- Приватное поле аннотируется при присваивании:
  `self._config: AppConfig = config`.
- Используется `Optional[T]`, пока репозиторий явно не перешёл на `T | None`.
- Для callback и coroutine используются точные `Callable`, `Awaitable`,
  `Coroutine`, если сигнатура известна.
- Общие контракты выражаются через `Protocol` либо `ABC` и
  `@abstractmethod`.
- Простые неизменяемые данные оформляются через `@dataclass(frozen=True)`, если
  им не нужна валидация.
- Конфигурации оформляются через Pydantic `BaseModel` с явными полями. Для
  внешней конфигурации запрещаются неизвестные ключи через
  `ConfigDict(extra='forbid')`, если совместимость не требует иного.

### Документация

- Комментарии и docstring пишутся на русском языке.
- Docstring использует тройные двойные кавычки и стиль Google.
- Короткая функция с очевидным контрактом получает однострочный docstring.
  Развёрнутый начинается с резюме, затем после пустой строки описывает контракт.
- Все публичные классы, функции и методы документируются. Приватная сущность
  документируется при неочевидной протокольной роли или ограничении.
- Используются `Args:`, `Returns:`, `Raises:`. Типы не дублируются, если
  они однозначно заданы аннотациями.
- Для класса при необходимости используется `Attributes:`; описываются
  ответственность атрибута и инвариант, а не его тип.
- Комментарий объясняет протокол, момент создания события, владение задачей,
  причину блокировки или обработку ошибки, а не очевидное присваивание.

```python
async def send_command(command: bytes, timeout: float) -> bool:
	"""Отправляет команду и ожидает подтверждение контроллера.

	Args:
		command: Команда в двоичном формате.
		timeout: Максимальное время ожидания подтверждения, с.

	Returns:
		`True`, если подтверждение получено.

	Raises:
		asyncio.TimeoutError: Контроллер не ответил вовремя.
	"""
```

### Форматирование и асинхронный код

- Строковые литералы по умолчанию используют одинарные кавычки, docstring —
  тройные двойные. В существующем модуле сохраняется выбранный стиль.
- Длинные сигнатуры и вызовы переносятся в скобках. В многострочном вызове
  аргументы размещаются по одному на строку с завершающей запятой.
- Обратная косая черта для переноса выражений не используется.
- Короткий однородный блок полей или констант разрешается выравнивать, если
  форматтер репозитория не отменяет это выравнивание.
- Правый комментарий подходит для единицы измерения или короткого состояния;
  длинное объяснение размещается над строкой.
- При работе с текстовыми файлами указывается `encoding='utf-8'`.
- Фоновые задачи, события, очереди и блокировки хранятся в явно аннотированных
  приватных атрибутах.
- Момент создания `Event`, `Lock` или задачи комментируется, если от него
  зависит протокол или привязка к event loop.
- Задача из `asyncio.create_task()` имеет владельца, сохраняется в атрибуте
  или коллекции и штатно отменяется при завершении.
- Ожидание внешнего ответа ограничивается таймаутом, если бесконечное ожидание
  не является явно описанным контрактом.
- `asyncio.CancelledError` не скрывается без необходимой очистки и дальнейшего
  распространения, кроме случая, когда отмена — ожидаемый локальный результат.

## Локальные дополнения

Репозиторий может уточнять эти правила в собственной документации и закреплять
их форматтером или статическим анализатором. Локальное исключение должно быть
явным и не должно ослаблять требования безопасности и качества организации.
