# Git workflow

Этот документ описывает правила работы с Git в репозиториях команды.

Если вы только начинаете работать с Git, полезно знать несколько терминов:

- **репозиторий** — папка проекта вместе с историей изменений;
- **коммит** — сохранённый набор связанных изменений;
- **ветка** — отдельная линия работы, которая не мешает основной версии проекта;
- **Pull Request (PR)** — запрос на проверку и добавление изменений из ветки в проект;
- **ревью** — проверка изменений другим участником команды.
  
Подробнее про работу с git и github можно посмотреть [тут](https://youtu.be/VJm_AjiTEEc?si=5s-wpJSXPtdhVGIc) и [тут](https://youtu.be/F7FnnfnB9YY?si=hro-8N-sfwd_vrE8) 

Обычный путь изменения выглядит так:

```text
GitHub Issue → рабочая ветка → Pull Request → ревью → master
```

## Основная ветка

`master` — единственная постоянная ветка. Она должна содержать актуальную версию кодовой базы.

Прямые изменения в `master` запрещены. Любые изменения попадают в неё только через Pull Request после ревью.

Перед началом новой задачи нужно обновить локальную версию `master`, а затем создать от неё отдельную рабочую ветку. Не работайте прямо в `master`.

## Рабочие ветки

Каждая нетривиальная задача начинается с GitHub Issue. Для её выполнения от актуального `master` создаётся отдельная ветка.

Используются следующие форматы имён:

```text
feature/<номер-задачи>
bugfix/<номер-задачи>
task/<номер-задачи>
```

Примеры:

```text
feature/42
bugfix/57
task/63
```

Одна ветка соответствует одной логической задаче. Если задача слишком велика для одного Pull Request, её следует разбить на несколько самостоятельных Issues.

В рабочей ветке делайте небольшие понятные коммиты. Сообщение коммита должно объяснять изменение, например: `Добавить настройку UART` или `Исправить обработку тайм-аута`.

## Pull Request и ревью

После завершения работы разработчик создаёт Pull Request из рабочей ветки в `master`.

В описании Pull Request указывается связанная задача:

```text
Closes #42
```

После merge GitHub автоматически закроет соответствующий Issue.

Перед созданием Pull Request синхронизируйте рабочую ветку с актуальным `master` и разрешите конфликты, если они появились.

Для слияния Pull Request должны быть выполнены условия:
- все комментарии ревью разрешены;
- после новых коммитов Pull Request проверяется и одобряется заново;
- запрещены прямые push, force push.

В `master` используется только **Squash merge**: все коммиты Pull Request объединяются в один итоговый коммит.

Это сохраняет историю `master` короткой и понятной: один PR соответствует одному логическому изменению.

## Релизы

Когда версия готова к стабилизации, от `master` создаётся временная ветка:

```text
release/<версия>
```

Например:

```text
release/0.2.0
```

В релизной ветке допустимы только исправления ошибок, подготовка документации и другие изменения, необходимые для выпуска. Новые функции в неё не добавляются.

После проверки на итоговый коммит релизной ветки ставится тег версии:

```text
v0.2.0
```

Если в релизной ветке появились исправления, их нужно вернуть в `master` через Pull Request. После выпуска релизную ветку можно удалить: точная версия остаётся доступна по тегу.

## Синхронизация

Перед началом новой работы и перед открытием Pull Request разработчик синхронизирует рабочую ветку с актуальным `master` и разрешает возникающие конфликты.

## Чего нельзя делать

- выполнять прямой push в `master`;
- удалять или принудительно переписывать историю `master`;
- вливать собственный PR без ревью;
- добавлять в один PR изменения из разных независимых задач;
- помещать новую функциональность в релизную ветку.
