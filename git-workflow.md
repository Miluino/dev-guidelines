# Git workflow

Этот документ описывает правила работы с Git в репозиториях команды.

Если вы только начинаете работать с Git, полезно знать несколько терминов:

- **репозиторий** — папка проекта вместе с историей изменений;
- **коммит** — сохранённый набор связанных изменений;
- **ветка** — отдельная линия работы, которая не мешает основной версии проекта;
- **Pull Request (PR)** — запрос на проверку и добавление изменений из ветки в проект;
- **ревью** — проверка изменений другим участником команды.
  
Подробнее про работу с git и github можно посмотреть [тут](https://youtu.be/VJm_AjiTEEc?si=5s-wpJSXPtdhVGIc) и [тут](https://youtu.be/F7FnnfnB9YY?si=hro-8N-sfwd_vrE8) 

Обычный путь изменения выглядит так:

```text
GitHub Issue → рабочая ветка → Pull Request → ревью → master
```

## Основная ветка

`master` — единственная постоянная ветка. Она должна содержать актуальную версию кодовой базы.

Прямые изменения в `master` запрещены. Любые изменения попадают в неё только через Pull Request после ревью.

Перед началом новой задачи нужно обновить локальную версию `master`, а затем создать от неё отдельную рабочую ветку. Не работайте прямо в `master`.

## Рабочие ветки

Каждая нетривиальная задача начинается с GitHub Issue. Для её выполнения от актуального `master` создаётся отдельная ветка.

Используются следующие форматы имён:

```text
feature/<номер-задачи>
bugfix/<номер-задачи>
task/<номер-задачи>
```

Примеры:

```text
feature/42
bugfix/57
task/63
```

Одна ветка соответствует одной логической задаче. Если задача слишком велика для одного Pull Request, её следует разбить на несколько самостоятельных Issues.

В рабочей ветке делайте небольшие понятные коммиты. Сообщение коммита должно объяснять изменение, например: `Добавить настройку UART` или `Исправить обработку тайм-аута`.

## Создание рабочей ветки

Перед началом задачи обновите локальный `master` и создайте от него рабочую ветку. Команды одинаково работают в PowerShell и в Linux-терминале:

```text
git switch master
git pull --ff-only origin master
git switch -c task/123-uart-timeout
```

Вместо `task/123-uart-timeout` используйте имя, соответствующее типу и номеру вашего Issue. Например, для новой функции подойдёт `feature/42-uart`, а для ошибки — `bugfix/57-spi-timeout`.

Изменения сохраняются в рабочей ветке обычными коммитами:

```text
git status
git add <файлы>
git commit -m "Исправить тайм-аут UART"
```

Не используйте `git add .`, если не понимаете, какие именно файлы будут добавлены в коммит. Сначала проверяйте вывод `git status`.

## Локальные вспомогательные ветки

При необходимости от рабочей ветки можно создать локальную вспомогательную ветку: например, для эксперимента, рефакторинга или отдельной части большой задачи. Такая ветка не заменяет рабочую и не требует отдельного Pull Request.

```text
git switch task/123-uart-timeout
git switch -c local/task/123-uart-parser
```

После работы в ней сохраните изменения коммитом, вернитесь в рабочую ветку и влейте вспомогательную ветку в неё:

```text
git add <файлы>
git commit -m "Выделить обработчик UART"
git switch task/123-uart-timeout
git merge local/task/123-uart-parser
```

Затем рабочая ветка отправляется на GitHub как обычно. Вспомогательная ветка остаётся только локальной; не выполняйте для неё `git push`, если администратор или тимлид не попросил об этом отдельно.

Если часть работы требует отдельного ревью или может стать самостоятельной задачей, создайте для неё отдельный Issue и рабочую ветку, а не локальную вспомогательную ветку.

## Pull Request и ревью

### 1. Отправьте рабочую ветку на GitHub

После завершения задачи или когда нужна ранняя проверка отправьте ветку на GitHub:

```text
git push -u origin task/123-uart-timeout
```

Параметр `-u` связывает локальную ветку с удалённой. При следующих изменениях достаточно команды:

```text
git push
```

### 2. Синхронизируйте ветку с `master`

Перед созданием Pull Request получите актуальное состояние удалённого репозитория и влейте его `master` в свою рабочую ветку:

```text
git switch task/123-uart-timeout
git fetch origin
git merge origin/master
```

Если возникнут конфликты, разрешите их, проверьте результат, завершите merge-коммит и отправьте ветку повторно:

```text
git add <исправленные-файлы>
git commit
git push
```

### 3. Откройте Pull Request

После завершения работы разработчик создаёт Pull Request из рабочей ветки в `master`.

На GitHub укажите:

- **base** — `master`;
- **compare** — ваша рабочая ветка, например `task/123-uart-timeout`;
- понятный заголовок, описывающий результат;
- выполненные проверки: тесты, сборку, проверку на плате или проверку документации.

В описании Pull Request указывается связанная задача:

```text
Closes #42
```

После merge GitHub автоматически закроет соответствующий Issue.

### 4. Пройдите ревью

Запросите ревью у другого участника команды. Для слияния Pull Request должны быть выполнены условия:

- есть хотя бы одно одобрение другого участника;
- все комментарии ревью разрешены;
- после нового коммита прежнее одобрение сбрасывается, поэтому нужен повторный review;
- выполнены обязательные проверки, если они настроены в репозитории.

Если ревьюер оставил замечания, исправьте их в той же рабочей ветке и отправьте новые коммиты:

```text
git switch task/123-uart-timeout
git add <файлы>
git commit -m "Учтены замечания ревью"
git push
```

Не создавайте для исправлений отдельный Pull Request: они должны появиться в уже открытом PR.

### 5. Влейте Pull Request

В `master` используется только **Squash merge**: все коммиты Pull Request объединяются в один итоговый коммит.

Это сохраняет историю `master` короткой и понятной: один PR соответствует одному логическому изменению.

После approval, закрытия обсуждений и прохождения проверок выполните в GitHub **Squash and merge**. Локально сливать рабочую ветку в `master` не нужно: итоговое слияние выполняется на GitHub.

После merge обновите локальный `master` перед следующей задачей:

```text
git switch master
git pull --ff-only origin master
```

## Если рабочая ветка случайно слита в локальный `master`

GitHub защищает удалённый `master`, но не запрещает локальный merge. Поэтому случайная команда `git merge task/123-uart-timeout`, выполненная в локальном `master`, не опасна сама по себе. Проблема возникнет только при попытке отправить такой `master` на GitHub: Ruleset отклонит `git push origin master`.

Если это произошло:

1. Не выполняйте `git push origin master` и не используйте `git push --force`.
2. Убедитесь, что рабочая ветка с изменениями существует. Если она есть, отправьте именно её и откройте Pull Request:

   ```text
   git switch task/123-uart-timeout
   git push -u origin task/123-uart-timeout
   ```

3. После этого вернитесь в локальный `master`, создайте резервную ветку и синхронизируйте его с GitHub:

   ```text
   git switch master
   git status
   git branch backup/accidental-master-merge
   git fetch origin
   git reset --hard origin/master
   ```

`git reset --hard origin/master` удаляет все несохранённые изменения в локальном `master`. Выполняйте его только после проверки `git status`, создания резервной ветки и подтверждения, что нужные коммиты сохранены в рабочей ветке.

Если рабочая ветка уже удалена, но нужные коммиты остались в локальном `master`, сначала создайте от него новую рабочую ветку и отправьте её на GitHub:

```text
git switch master
git switch -c task/123-recovered
git push -u origin task/123-recovered
```

Затем откройте Pull Request и только после этого приводите локальный `master` к состоянию `origin/master`.

## Релизы

Когда версия готова к стабилизации, от `master` создаётся временная ветка:

```text
release/<версия>
```

Например:

```text
release/0.2.0
```

В релизной ветке допустимы только исправления ошибок, подготовка документации и другие изменения, необходимые для выпуска. Новые функции в неё не добавляются.

После проверки на итоговый коммит релизной ветки ставится тег версии:

```text
v0.2.0
```

Если в релизной ветке появились исправления, их нужно вернуть в `master` через Pull Request. После выпуска релизную ветку можно удалить: точная версия остаётся доступна по тегу.

## Синхронизация

Перед началом новой работы обновляйте локальный `master`. Перед созданием Pull Request синхронизируйте с ним рабочую ветку и разрешайте возникающие конфликты.

## Чего нельзя делать

- выполнять прямой push в `master`;
- удалять или принудительно переписывать историю `master`;
- сливать рабочую ветку в локальный `master` вместо создания Pull Request;
- вливать собственный PR без ревью;
- добавлять в один PR изменения из разных независимых задач;
- помещать новую функциональность в релизную ветку.
