# Работа с GitHub Issues и GitHub Projects

Этот документ объясняет, как команда планирует работу и отслеживает задачи в
GitHub.

## Коротко о главном

**GitHub Issue** — карточка одной задачи: новой функции, ошибки, исследования
или другой работы.

**GitHub Project** — общая доска команды. Она показывает задачи из Issues, их
состояние, исполнителей и приоритеты.

```text
Issue #42 «Добавить драйвер UART»
        ↓
ветка feature/42
        ↓
Pull Request
        ↓
задача закрыта, карточка находится в Done
```

Issue хранит подробности задачи и обсуждение. Project помогает увидеть всю
работу команды сразу.

## Когда создавать Issue

Создавайте Issue до начала любой работы, если для её выполнения необходимо:
- менять код, схему или документацию;
- исправлять ошибку.

Если есть сомнения, лучше создать Issue: лишняя карточка проще, чем потерянная задача.

## Как оформить Issue

Заголовок должен коротко отвечать на вопрос «что нужно сделать»:

```text
Добавить драйвер UART
Исправить ошибку чтения SPI
Проверить возможность питания от USB
```

В описании укажите:

```text
Цель
Какой результат должен быть получен.

Что нужно сделать
Основные шаги или границы задачи.

Критерии готовности
- Что должно работать.
- Как понять, что задача завершена.

Дополнительная информация
Ссылки, схемы, примеры, ограничения.
```

Для сообщения об ошибке дополнительно напишите:

```text
Как воспроизвести ошибку
Что произошло
Что должно было произойти
```

## Поля задачи

У Issue есть несколько важных полей:

| Поле | Что в нём указывать |
|---|---|
| Assignee | Кто отвечает за выполнение задачи |
| Labels | Тип и область работы: `bug`, `feature`, `firmware`, `hardware` |
| Milestone | Версия или этап, в который должна войти задача |
| Project | Общая доска команды |

Исполнитель отвечает за движение задачи, но может просить помощь у других
участников.

## Статусы в Project

На общей доске используются следующие статусы:

| Статус | Значение |
|---|---|
| Backlog | Идея или задача записана, но ещё не готова к началу |
| Ready | Задача понятна, её можно брать в работу |
| In progress | Исполнитель работает в своей ветке |
| In review | Открыт Pull Request, идёт ревью |
| Done | Pull Request принят и изменения попали в `master` |

Задачу переводят в `In progress`, когда исполнитель начинает работу и создаёт
ветку. После создания Pull Request её переводят в `In review`. После merge в
`master` — в `Done`.

## Связь Issue, ветки и Pull Request

Номер Issue используется в имени рабочей ветки:

```text
Issue #42 → feature/42
Issue #57 → bugfix/57
```

В описании Pull Request добавьте:

```text
Closes #42
```

После merge GitHub автоматически закроет Issue. Это связывает задачу, ветку,
изменения и ревью в одну историю.

Подробнее о работе с ветками и Pull Request написано в
[git-workflow.md](dev-guidelines/git-workflow.md).

## Большие задачи и зависимости

Большую цель можно разбить на несколько меньших Issues. Например:

```text
Issue: Поддержка UART
├─ Issue: Настройка периферии
├─ Issue: Передача данных
├─ Issue: Приём данных
└─ Issue: Проверка на плате
```

Если одна задача не может начаться до завершения другой, укажите зависимость в
GitHub: какая задача блокируется (**blocked by**) другой. Это помогает команде видеть реальные
блокировки.

## Релизы

Для каждой готовящейся версии создайте Milestone, например `v0.2.0`, и добавьте
в него Issues, которые должны войти в релиз.

Когда все нужные задачи в milestone завершены, тимлид (или разработчик по его указанию) создаёт релизную ветку и
проверяет версию по правилам из [git-workflow.md](dev-guidelines/git-workflow.md).

## Короткий порядок работы

```text
1. Создать или выбрать Issue.
2. Уточнить результат и назначить исполнителя.
3. Перевести задачу в Ready.
4. Создать рабочую ветку с номером Issue.
5. Перевести задачу в In progress.
6. Создать Pull Request и перевести задачу в In review.
7. Пройти ревью и влить PR в master.
8. Убедиться, что Issue закрыт, а карточка в Project находится в Done.
```

## Чего избегать

- не начинать крупную работу без Issue;
- не создавать одну карточку на несколько независимых задач;
- не менять статус задачи, если реальное состояние работы другое;
- не закрывать Issue до принятия связанного Pull Request;
- не хранить техническое решение только в чате: важные договорённости нужно
  добавлять в Issue или Pull Request.
